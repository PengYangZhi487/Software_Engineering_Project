开发思路？
1.立项与选题>2.可行性研究与技术原型>3.需求分析>4.概要设计>5.详细设计>6.实现与集成>7.测试>8.部署与交付>9.维护与项目总结
不要做成“严格瀑布、一次线性走完”，而是采用：阶段化推进 + 小回流迭代 + 纵向切片实现

1.立项与选题
基于大语言模型的软件需求分析与测试用例辅助生成平台的设计与实现
把软件项目的需求文档转化为结构化、可检查、可追踪的需求，并辅助生成测试用例，让开发团队更容易发现需求问题、验证软件功能，以及管理需求变更带来的影响。

问题 1：需求写得不清楚，开发人员理解不一致
假设正在开发一个校园选课系统，产品需求中写着：
系统应允许学生在规定时间内选课，并在课程人数达到上限时禁止继续选课。
这段话看起来没有问题，但实际上存在多个未明确的地方：
- “规定时间”具体是什么时间？
- 课程人数达到上限时，是否允许已选学生退课后重新选课？
- 两名学生同时选择最后一个名额时，如何处理？
- 选课失败时，系统需要给出什么提示？
- 学生重复提交选课请求时，会不会重复选课？
如果这些问题没有在开发前明确，开发人员可能按照自己的理解实现，测试人员也可能按照另一套理解编写测试。
平台可以帮助把这段描述拆解成具体的待确认问题，并提示可能需要补充的边界条件。
例如：
待确认的需求问题
原始需求：课程人数达到上限时，禁止继续选课。
系统建议进一步明确：
- 当剩余名额为 1 时，两名学生同时请求选课，是否只允许一人成功？
- 选课人数达到上限后，退课是否会释放名额？
- 选课失败时，是否需要明确返回“课程已满”的提示？
这些是需要产品人员确认的候选问题，不代表系统已经证明原始需求存在错误。
注意：AI 无法仅凭这句话确定业务方真正想要什么。它能发现值得确认的地方，但不能擅自替业务方做决定。

问题 2：测试用例依赖人工编写，容易遗漏边界条件
有了需求之后，测试人员还需要回答：
- 哪些场景必须测试？
- 正常情况怎么测试？
- 异常情况怎么测试？
- 输入的边界值是什么？
- 预期结果应该是什么？
例如，针对“课程最多容纳 50 名学生”的需求：
测试场景	                          前置条件	                        预期结果
正常选课	                          当前 20 人	                        选课成功
最后一个名额	                  当前 49 人	                        一名学生选课成功
课程已满	                          当前 50 人	                        新选课请求失败
两人竞争最后一个名额	  当前 49 人	                        最多一人成功
重复提交	                          同一学生重复提交请求	不应产生重复选课记录，具体规则需确认
平台可以根据需求生成这些候选用例，再让用户修改和审核。
这里还有一个重要区别：AI 生成的测试用例，不等于这些测试已经执行过，更不等于软件已经通过测试。若要验证软件是否符合需求，还需要实际运行测试。

问题 3：需求变化之后，不知道哪些测试需要修改
假设项目初始规定课程最多 50 人，后来改成最多 60 人。
开发人员不只是修改一处数字，还需要确认：
- 哪些需求说明需要更新？
- 哪些测试用例的预期结果需要调整？
- 哪些边界值需要重新验证？
- 哪些测试结果已经过时？
如果需求、测试用例和版本信息分散在 Word、Excel、聊天记录中，就容易出现遗漏。
平台可以保存这些对象之间的关联，需求修改后自动列出关联测试用例，供测试人员检查。
这时，软件的价值就不只是生成文本，而是持续管理整个项目中的需求与验证关系。



系统应当有哪些模块?
建议将系统划分为 6 个核心模块。这里最重要的原则是：每个模块都应当对应一个真实的软件工程任务，而不是单纯为了增加功能数量。

模块 1：需求文档管理
解决需求文档散落、版本混乱的问题。
- 上传 PDF、DOCX、TXT 等文件。
- 解析文档正文，保存原始文件。
- 管理项目、文档版本和导入记录。
- 保留原文页码或段落位置，便于追溯。

模块 2：结构化需求管理
把自然语言文档转化成可管理的需求条目。
- 自动提取候选需求。
- 为需求分配唯一编号，如 REQ-001。
- 标记功能需求、非功能需求等类型。
- 编辑需求描述、优先级、状态和验收标准。
- 支持人工确认、拒绝和修改 AI 的提取结果。

模块 3：需求质量分析
帮助发现需要人工审查的风险。
- 检查模糊表达，例如“尽快”“足够快”。
- 识别语义相近的需求。
- 提示可能的逻辑冲突。
- 检查是否缺少可验证的验收条件。
- 显示问题依据、风险等级和处理状态。
AI 提供候选判断，确定性规则负责可明确判定的检查，最终结论由用户审核。

模块 4：测试用例生成与管理
把需求转换成可审核、可执行的测试方案。
- 生成正常、异常和边界场景。
- 保存前置条件、操作步骤、预期结果。
- 支持修改、审核、拒绝和导出。
- 记录测试用例版本和执行状态。
- 区分“已生成”“已审核”和“已执行”。

模块 5：需求追踪与变更分析
把需求和测试用例关联起来，并管理版本变化。
- 建立需求与测试用例之间的多对多关联。
- 查询某项需求对应哪些测试用例。
- 比较两个版本的需求差异。
- 定位可能受影响的测试用例。
- 由用户确认哪些用例需要更新或重新执行。

模块 6：质量统计与报告
用可核查的数据展示项目质量状态。
- 统计需求总数和待确认问题数。
- 计算需求测试关联覆盖率。
- 统计测试用例审核和执行状态。
- 生成需求追踪矩阵及质量报告。
- 导出 CSV、Excel 或可编辑报告。



一个用户实际使用这个系统的完整流程
以“校园选课系统”为示例，模拟一次完整的使用过程。

01创建项目并上传文档
用户创建选课系统项目，上传需求规格说明书。系统解析文本，并保留原始文档位置。

02提取结构化需求
系统识别出选课时间、课程容量、重复选课等候选需求，并分配唯一编号。

03分析需求质量
系统发现“系统应快速响应”缺少具体指标，提示用户补充响应时间要求。

04人工审核需求
用户确认需求内容，修改错误的提取结果，并为需求补充验收条件。

05生成测试用例
系统根据确认后的需求生成正常、异常和边界测试用例，用户审核后保存。

06查看需求追踪关系
用户检查每项需求是否有关联的测试用例，找出尚未覆盖的需求。

07处理需求变更
用户修改课程容量要求，系统对比新旧版本，列出相关测试用例供用户复核。

08导出质量报告
系统生成需求清单、问题列表、追踪矩阵、测试用例及覆盖率统计。

这条流程也是开发时最重要的验收主线。最终演示时，应当能够从一份原始需求文档开始，一步步展示到结构化需求、测试用例、变更影响和质量报告，而不是单独演示几个互不关联的页面。



系统的核心技术应该是什么？
如果只用一个前端页面调用大模型 API，项目的技术深度会比较有限。
要让它成为真正的软件工程项目，我建议从以下四个方面设计。
1. 需求结构化与质量检查
原始需求是一段自然语言，系统需要将它转化成固定的数据结构。
例如：
{
  "requirement_id": "REQ-002",
  "title": "课程人数限制",
  "description": "每门课程最多容纳50名学生",
  "type": "functional",
  "priority": "high",
  "acceptance_criteria": [
    "当前人数小于50时允许选课",
    "当前人数达到50时拒绝新选课"
  ],
  "source": {
    "document": "选课系统需求说明书",
    "page": 3
  },
  "status": "reviewed"
}
这只是建议的数据格式。实际实现时，还应验证字段类型、必填字段、编号唯一性和原文位置是否有效。
需求质量检查可以分成两种：
- 规则检查： 检查空描述、缺少验收条件、重复编号、未填写字段等确定性问题。
- 语义检查： 借助 AI 发现模糊描述、潜在冲突和遗漏风险。
两者结合，比把所有工作都交给 AI 更可靠。
2. 测试用例生成
测试用例需要有明确的字段，而不是一段自然语言回答。
{
  "test_case_id": "TC-015",
  "requirement_id": "REQ-002",
  "title": "课程达到容量上限后拒绝选课",
  "preconditions": [
    "课程当前已有50名学生"
  ],
  "steps": [
    "以另一名未选课学生的身份提交选课请求"
  ],
  "expected_result": "选课失败，课程人数保持不变",
  "test_type": "boundary",
  "status": "pending_review"
}
系统需要检查 AI 返回的结果是否符合数据结构，并确认它引用的需求确实存在。用户审核后，才把它作为正式测试用例保存。
注意，示例中的预期结果依赖业务规则。如果实际需求没有规定失败提示、并发行为或数据一致性，就不能让系统假定这些规则已经得到确认。
3. 需求追踪与变更影响分析
这是我认为该项目最应该做扎实的部分。
可以将需求、测试用例和它们之间的关联存入数据库：
- requirements：需求信息及版本。
- test_cases：测试用例及版本。
- requirement_test_links：需求与测试用例的关联。
- documents：原始文档与版本。
- review_issues：需求审查发现的问题。
- test_runs：实际测试执行记录。
当需求发生变化时，系统先对比新旧版本，再查询关联关系，找出需要复核的测试用例。
需要区分两个概念：
- 关联影响： 某个测试用例关联了变更需求，因此需要检查。
- 实际影响： 测试用例的步骤或预期结果确实需要修改。
系统可以自动识别前者，但后者往往需要结合变更内容和人工判断，不能简单地认为所有关联用例都必须修改。
4. 质量指标与自动化验证
这个模块可以让你们证明项目有实际效果。
例如，可以统计：需求测试关联覆盖率=(至少关联一个测试用例的需求数/纳入统计的有效需求总数)*100%
还可以统计：
- 需求提取准确率。
- 模糊需求提示的准确率。
- 测试用例人工审核通过率。
- 需求变更影响识别的准确率与召回率。
- 文档解析失败率。
- 系统接口测试通过率。
这些指标各自衡量不同的东西。尤其是“测试用例生成数量多”不代表测试质量高，关联覆盖率也不等于真正发现了缺陷的能力。



AI 在这个系统中到底负责什么？
这是选题中需要提前划清的边界。
任务	                                                                                    建议实现方式	                                                    为什么
文档上传与存储	                                                                    普通程序逻辑	                                                    不需要 AI
PDF、Word 文本提取	                                                            文档解析库	                                                    结果更可控
需求编号与版本记录	                                                            数据库与业务逻辑	                                            必须保证稳定性
检查必填字段	                                                                    规则引擎	                                                            可以确定性判断
识别模糊描述	                                                                    规则 + AI	                                                            需要理解自然语言
发现潜在语义冲突	                                                            AI 辅助 + 人工审核	                                            很多情况依赖上下文
生成测试用例	                                                                    AI 辅助生成	                                                    自然语言到测试场景的转换适合大模型
检查引用的需求是否存在	                                                    程序校验	                                                            不应依赖模型自我保证
计算覆盖率	                                                                            数据库查询与程序计算	                                    需要可重复的精确结果
比较需求版本	                                                                    文本差异算法 + 语义辅助	                            精确差异和语义变化需要不同方法
导出报告	                                                                            模板与程序逻辑	                                            不需要 AI
一个重要的设计原则是：AI 负责提出候选结果，软件负责管理、验证和追踪结果。
例如，AI 可以判断两条需求可能存在冲突，但不应该直接修改正式需求；AI 可以生成测试用例，但不应该把未审核的用例自动标记为“测试通过”。另外，如果没有 AI，系统仍然应该可以完成文档管理、需求编辑、测试用例管理、追踪矩阵、版本比较和报告导出。这样才符合“AI 是辅助功能”的目标。



第一版应该做多大？哪些功能必须完成？
不建议一开始就实现前面列出的全部功能。对于课程项目，最好先做一个完整但范围受控的 MVP（最小可行产品）。
第一阶段：必须完成                             MVP
1. 上传一份需求文档，并解析出文本。
2. 提取或手动创建结构化需求，并分配唯一编号。
3. 提供基础规则检查和 AI 辅助需求分析。
4. 生成候选测试用例，允许人工修改、审核和保存。
5. 建立需求与测试用例的关联，展示追踪矩阵。
6. 统计需求测试关联覆盖率，并导出报告。
7. 至少实现基本的需求版本比较和受影响测试用例查询。
第二阶段：有时间再做
- 更复杂的语义冲突检测和重复需求识别。
- 多用户权限、审核工作流和操作审计。
- 连接真实测试框架，执行生成的测试。
- RAG、Agent 协作、复杂的自动化测试生成。
这里有一个容易忽略的重点：如果项目最终只有“需求提取 + 测试用例生成”，它仍然很容易被现成 AI 替代。建议至少把需求追踪、版本变更影响分析和质量统计纳入第一版核心范围，让软件形成完整的工程闭环。



如何证明这个项目真的有用？
课程项目不能只靠演示视频证明价值。你们可以准备一套固定的需求文档与人工标注结果，然后进行实验。

例如，准备一个校园选课系统的需求集，包含：
- 30–50 条需求。
- 一部分描述清晰的需求。
- 一部分存在模糊表达的需求。
- 几组重复或可能冲突的需求。
- 两个版本的需求文档。
- 一份人工编写并审核过的测试用例参考集。
再进行下面的实验。
实验	                                          评估方法	                                                                   能说明什么
需求提取	                                  与人工标注结果比较	AI                                               能否正确识别需求
模糊问题检测	                          比较提示与人工确认的问题	                                   是否有帮助发现需求风险
测试用例生成	                          人工审核通过率、需求关联情况	                           生成结果是否可用
版本变更分析	                          比较识别结果与人工标注的受影响用例	           系统是否会漏掉重要影响
端到端流程	                                  检查需求、测试、关联和报告是否一致	           工程流程是否可靠
建议特别关注两种指标：Precision=TP/(TP+FP)           Recall=TP/(TP+FN)
其中，\(TP\) 是正确识别的目标，\(FP\) 是误报，\(FN\) 是漏报。
例如，系统提示了 10 个可能存在问题的需求，其中 8 个经人工确认确实需要处理，那么这次检测的 Precision 为 80%。如果人工标注共有 20 个需要处理的问题，而系统识别出其中 8 个，那么 Recall 为 40%。
这两个指标可以帮助你们区分“系统很爱报警”和“系统真正能发现问题”这两种不同情况。
这里的数据只是举例，不能预先声称系统会达到某个准确率。实际结果应当通过实验获得。

2. MVP 7 项：完成线 / 降级线
M1 文档上传与解析	支持 TXT 和 DOCX 上传、解析正文、保留段落序号；PDF 可尝试但不作为承诺。	仅 TXT；DOCX 和 PDF 提示“暂不支持，可粘贴文本”。端到端主线仍可用粘贴文本代替上传。

M2 结构化需求与编号	AI 提取 + 手动创建均可；自动分配唯一编号；支持编辑、确认、拒绝；字段含标题、描述、类型、优先级、验收标准、原文位置、状态。	AI 提取不可用时可完全手动创建；编号唯一性和必填字段校验保留。

M3 规则检查 + AI 辅助质量分析	规则检查空描述、缺验收条件、重复编号、必填字段；AI 对模糊表达和遗漏风险给出候选提示，人工可标记“确认/忽略”。	AI 检查降级为“模糊词表规则提示”；复杂冲突检测不做；规则检查结果仍可展示。

M4 候选测试用例生成与审核	对已确认需求生成正常/异常/边界候选用例；schema 校验通过；支持人工修改、审核、拒绝；区分“已生成/已审核/已执行”。	AI 生成降级为“模板 + AI 补全”或仅生成正常/边界两类；人工可手动创建用例；审核状态保留。

M5 需求-用例关联与追踪矩阵	多对多关联可建立、可查询；追踪矩阵展示“需求→关联用例”和“未覆盖需求”；支持按需求查用例。	关联改为手动建立；矩阵展示保留；自动推荐关联不做。

M6 覆盖率统计与报告导出	覆盖率 = 至少关联一个用例的需求数 / 有效需求总数 × 100%；可页面展示、可 CSV 导出；导出数字与页面一致。	仅 CSV 导出；Excel/可编辑报告格式降级；覆盖率计算和展示保留。

M7 版本比较与受影响用例查询	两版需求文档可按需求条目对齐，用精确文本差异（如 difflib）定位数字/描述变更；查询变更需求的关联用例并列出供人工复核；区分“关联影响”和“需人工确认的实际影响”。   降级线： 版本对齐改为“需求编号 + 人工确认”；语义差异辅助不做；精确文本差异（difflib）和“按变更需求查关联用例列表”保留；覆盖率与报告不受影响。

3. 二期范围（本期不做，记录为候选）
更复杂的语义冲突检测和重复需求识别；
多用户权限、审核工作流和操作审计；
连接真实测试框架，执行生成的测试；
RAG、Agent 协作、复杂自动化测试生成；
PDF 稳定解析与更细粒度原文定位；
自动判定“实际影响”（而非仅列出关联影响）。
保留理由： 这些功能不阻塞 G1 端到端主线；在单人 + 有限周期下，优先保证追踪、变更查询和可复算统计做扎实。

4. 明确不做项及理由
不做项	理由
AI 输出直接作为正式需求，无需人工确认	违背“AI 提候选、人做决策”的边界；需求错误会向下游传播。
AI 生成用例自动标记为“测试通过/已执行”	生成≠执行；是否通过必须由实际运行或人工审核决定。
承诺任何准确率、通过率数值	指标必须来自实际实验，立项阶段不预设结果。
复杂语义冲突全自动判定	上下文依赖强，单人项目不可控，放二期或不做。
多用户权限与完整审核工作流	不服务于 G1 端到端主线，挤占核心功能工时。
真实测试框架执行与测试运行管理	超出 MVP 闭环，且需要额外环境与适配。

5. 实验数据来源与试标计划
来源意向： 自编为主。以“校园选课系统”为背景编写 20–30 条需求，覆盖清晰需求、模糊表达（“尽快”“足够好”）、重复或可能冲突的需求；在此基础上造两版本文档（如容量 50→60、选课时间规则变化）；参考用例集由本人编写并审核。
试标计划： 先写 10 条需求 + 1 页标注规则，自己标注并记录工时和分歧点，用于 P7 估算全量标注和审核工作量。全量规模是否从 20–30 条上调到 30–50 条，由 P7 工时估算决定，不在本卡中承诺。

6. 技术栈意向（意向 + 备选，不锁死）
层次	意向	备选	说明
原型界面	Streamlit 或 Gradio	简易 HTML + FastAPI	优先快速验证流程，不先做复杂前端。
后端	FastAPI（Python）	Flask	与文档解析、LLM 调用同语言，单人维护成本低。
数据库	SQLite（原型/开发）	PostgreSQL（如需部署）	原型阶段 SQLite 足够；表结构按需求、用例、关联、文档、问题、执行记录设计。

版本比较	difflib 精确文本差异	人工确认对齐	语义差异辅助放二期。
LLM 调用	OpenAI 兼容接口	各厂商原生 SDK	便于切换模型。
校验	Pydantic / JSON Schema	手写校验函数	需求和用例的 schema 校验。
测试	pytest + 接口测试	Postman	覆盖解析、校验、关联查询、覆盖率计算。

7. LLM 选型候选与预算估算框架  deepseek  预算不高
主选：DeepSeek（OpenAI 兼容接口，JSON Output）。 理由：价格低、国内可得、JSON 可用；schema 合规靠 Pydantic 程序校验 + 重试，符合“AI 提候选、程序校验”的设计。
备选 1：通义千问 Qwen（百炼平台）。 理由：新用户免费额度大，适合原型密集调用；P2 实测时与 DeepSeek 对照合规率和成本。
备选 2：本地 Ollama 小模型。 理由：无网络/无预算时兜底验证流程，不追求生成质量。
预算上限： 原型 + 小规模实验阶段，API 自付总额不超过 50元；按“单次输入/输出 token × 预计调用次数 × 单价”估算，扣除免费额度后不超过该上限。最终主选由 P2 实测“首次 JSON 合规率 + 单次成本 + 账号可得性”决定，本卡不拍死。

前端/原型界面	                  没做过	                                 若没做过，用 Streamlit/Gradio 降低门槛。
后端 API	                                  没做过                                        若没做过，优先 FastAPI 最小接口。

规则引擎/校验	                  没做过                                         Pydantic 可降低难度。
测试	                                  没做过                                         pytest + 手工审核并用。
高风险格处理： “LLM 结构化输出”和“数据库追踪查询”若自评为“没做过”，必须在 P2 和 P5 中优先验证，并提前准备降级线（程序校验 + 重试；手动关联 + 简单 SQL 查询）。
虽然这些技术栈都没做过，但是利用AI工具以及个人的一定理解，我觉得可以先尝试一下先做点质量好的，然后再降级
“先做好再降级”的执行规则： 核心三项按完成线先冲，但设时间盒和降级触发，不无限死磕。
P2 LLM 结构化输出： 时间盒 1.5 天。首次 JSON 合规率 ≥ 80% 或重试后 ≥ 95% → 保留完成线；低于此阈值 → 降级为“AI 输出文本建议 + 程序强校验 + 人工表单补全”，停止调 prompt。
P4 用例生成： 时间盒 1 天。schema 合规率 ≥ 90%、小样本人工审核能区分“可用/需修改/不可用” → 保留；否则降级为“模板 + AI 补全”，只生成正常/边界两类。
P5 追踪查询： 时间盒 1.5 天。按需求查用例、未覆盖查询、覆盖率复算三项跑通 → 保留；只能做前两项 → 版本比较降级为“人工选需求编号 + 查关联用例”；join 写不出 → 降级为手动关联 + 页面筛选，但覆盖率仍须可复算。
边缘功能一开始低配： 前端用 Streamlit/Gradio 不美化；PDF 不做；Excel 导出后补，先 CSV。
